# ContextPack Desktop — დამწყები მფლობელის უსაფრთხოების წესები

## პროექტის მფლობელის კონტექსტი

პროექტის მფლობელი დამწყები პროგრამისტია და სწავლობს მუშაობის პროცესში. მას ძირითადად Python-თან ჰქონია შეხება; PowerShell, Windows automation, Excel COM, installer და release engineering ჯერ კარგად არ იცის.

ეს სისუსტე არ არის და პროექტის განვითარებას არ უშლის ხელს, მაგრამ ნიშნავს, რომ AI-მ ცვლილებები არ უნდა გააკეთოს მხოლოდ ტექნიკური ანგარიშის მიწოდებით. ყოველი ეტაპი უნდა იყოს გასაგები, მცირე, შემოწმებადი და ადვილად დასაბრუნებელი.

## AI ასისტენტის სავალდებულო კომუნიკაცია

ყოველი მნიშვნელოვანი ცვლილების დაწყებამდე მარტივი ქართულით ახსენი:

1. რას ვცვლით;
2. რატომ გვჭირდება ცვლილება;
3. რომელი ფაილები შეიცვლება;
4. მომხმარებლისთვის ხილული ქცევა შეიცვლება თუ არა;
5. რა არის ყველაზე მნიშვნელოვანი რისკი;
6. რომელი ტესტი დაიცავს არსებულ ქცევას;
7. როგორ დავბრუნდებით წინა მუშა commit-ზე.

ცვლილების დასრულების შემდეგ ახსენი:

- რა დაემატა;
- რა გადავიდა ან წაიშალა;
- რა დარჩა განზრახ უცვლელი;
- რომელი unit/static/E2E ტესტები გავიდა;
- დარჩა თუ არა შეუმოწმებელი სცენარი;
- commit და remote branch-ის მდგომარეობა.

არ გამოიყენო მხოლოდ რთული ტერმინები. ტექნიკური ტერმინის გამოყენებისას ერთი წინადადებით განმარტე მისი მნიშვნელობა.

## რისკის რეალური წყაროები

ამ პროექტში ყველაზე მაღალი რისკის ნაწილებია:

- PowerShell scope და error handling;
- Windows paths და permissions;
- Microsoft Excel COM object lifecycle;
- workbook-ის read-only გახსნა;
- macro/event/external-link უსაფრთხოება;
- COM object release და დარჩენილი Excel პროცესები;
- atomic output replacement და rollback;
- installer და portable ZIP packaging;
- cleanup, რომელმაც მხოლოდ ზუსტად შემოწმებული დროებითი/output path უნდა წაშალოს.

AI-ს შეუძლია დამაჯერებლად დაწეროს არასწორი კოდი ან არასაკმარისი ტესტი. ამიტომ AI არ უნდა იყოს ცვლილების ერთადერთი „მტკიცებულება“ — მტკიცებულებაა tests, E2E, diff review და საჭიროებისას დამოუკიდებელი review.

## უსაფრთხო სამუშაო პროცესი

```text
მფლობელი განსაზღვრავს მიზანს
        ↓
AI ხსნის მცირე ტექნიკურ გეგმას მარტივი ქართულით
        ↓
ცვლილება კეთდება ცალკე refactor ბრენჩზე
        ↓
unit/static tests
        ↓
რეალური smoke ან სრული E2E
        ↓
diff review და ქართული შეჯამება
        ↓
მცირე commit და GitHub push
        ↓
მხოლოდ შემდეგ იწყება ახალი ეტაპი
```

## უცვლელი წესები

- პირდაპირ `main`-ში არ იმუშაო;
- `main`-ში merge ან release მომხმარებლის მკაფიო მითითების გარეშე არ გააკეთო;
- დიდი, ერთმანეთთან დაუკავშირებელი ცვლილებები ერთ commit-ში არ აურიო;
- refactor და ახალი feature ერთ milestone-ში არ აურიო;
- source დოკუმენტი არ შეცვალო და Excel-ში არ შეინახო;
- უსაფრთხოების არსებული check მხოლოდ იმიტომ არ წაშალო, რომ კოდი შემცირდეს;
- output schema შესაბამისი migration გეგმის გარეშე არ შეცვალო;
- installer/portable packaging ახალი code location-ისას ყოველთვის გადაამოწმე;
- მნიშვნელოვანი PDF/Excel/OCR ცვლილება მხოლოდ unit test-ით დასრულებულად არ ჩათვალო;
- Git history არ წაშალო და recoverable working state შეინარჩუნე;
- secrets, პირადი დოკუმენტები, API keys ან passwords repository-ში არ ატვირთო.

## ტესტირების მინიმალური დონეები

### მცირე pure-Python ცვლილება

- შესაბამისი unit tests;
- სრული Python suite;
- `git diff --check`.

### PowerShell routing/build ცვლილება

- სრული Python suite;
- `tests/test-common.ps1`;
- `tests/test-static.ps1`;
- შესაბამისი smoke test;
- `git diff --check`.

### PDF/Excel/OCR/COM ცვლილება

- ყველა ზემოთ ჩამოთვლილი;
- `tests/test-e2e.ps1 -RequireExcel`;
- დროებითი artifacts-ის cleanup-ის დადასტურება;
- Git working tree-ის შემოწმება.

### Installer/release ცვლილება

- source/static tests;
- installer build;
- clean install;
- launch;
- repair;
- uninstall;
- portable ZIP-ის ცალკე unpack-and-run შემოწმება.

## დამოუკიდებელი review

მაღალი რისკის milestone-ის შემდეგ სასურველია დამოუკიდებელი review, განსაკუთრებით:

- Excel COM lifecycle;
- macros/events/link security;
- atomic replacement/rollback;
- recursive cleanup;
- installer/uninstaller;
- release packaging.

Reviewer-ს პირველ ეტაპზე სთხოვე მხოლოდ პრობლემების და რისკების აღმოჩენა. Review და implementation ერთმანეთში ავტომატურად არ აურიო.

## დამწყებისთვის დოკუმენტაციის პრინციპი

ყველა მარტივი ხაზის კომენტარებით გადატვირთვა არ შეიძლება. უკეთესი მიდგომაა:

- თითოეულ მოდულს ჰქონდეს დანიშნულების მოკლე აღწერა;
- რთულ ფუნქციას ჰქონდეს docstring/comment-based help;
- კომენტარი ხსნიდეს „რატომ“-ს და არა აშკარა სინტაქსს;
- `docs/ARCHITECTURE.ka.md` აღწერდეს ნაწილების ურთიერთობას;
- მომავალში დაემატოს `docs/CODE_GUIDE.ka.md`, სადაც თითოეული მთავარი ფაილი დამწყებისთვის აიხსნება.

## როგორ შეფასდეს განცხადება „ყველაფერი მუშაობს“

არ თქვა „ყველაფერი სრულად მუშაობს“, თუ მხოლოდ unit tests გაიარა. ზუსტად მიუთითე:

- რა ტესტები გაეშვა;
- რომელი რეალური გზა შემოწმდა;
- რა არ შემოწმებულა;
- არსებობს თუ არა მხოლოდ დაბალი რისკის inference.

მაგალითად, Excel COM ცვლილების შემდეგ საკმარისი მტკიცებულებაა სრული `-RequireExcel` E2E, ხოლო მხოლოდ static pattern check — არა.

## მფლობელის სასწავლო მიზანი

რეფაქტორის დასრულებისას მფლობელს არ მოეთხოვება ყველა ტექნიკური დეტალის ცოდნა. მას ეტაპობრივად უნდა ესმოდეს:

- რომელი მოდული რას აკეთებს;
- სად იწყება პროგრამა;
- როგორ მოძრაობს input output package-მდე;
- რომელი უსაფრთხოების წესები არ უნდა დაირღვეს;
- როგორ გაუშვას ტესტები;
- როგორ ნახოს Git diff და commit history;
- როგორ დაბრუნდეს წინა მუშა commit-ზე დახმარების გარეშე ან მინიმალური დახმარებით.
